## Executive Summary

The fix is sound in its core claim: the line-identity migration predicate, the
malformed-marker refusal and the two-path de-duplication all hold up under
adversarial probing and under mutation testing, and every plan success criterion
(1–8) verifies green on this worktree. The `ai-os#138` shapes are genuinely
saved.

The TL;DR's stronger claim — "make `wiki_index.py` incapable of losing a byte" —
is **not** met. Marker recognition is an unanchored substring scan
(`text.count` / `text.index` over the raw file), so a `MEMORY.md` that merely
*mentions* both marker strings — in one sentence of prose, or in a fenced example
documenting the convention — has everything between them deleted silently, at
rc 0, with no `⚠`. That is one MAJOR finding with two reproductions. A second
class of defect, MINOR, is self-inflicted: because `build_index()` interpolates
frontmatter verbatim, a note whose `description` contains a marker string makes
the generator write a file it then refuses to touch ever again.

Test quality is above average — 13 of 18 injected mutants were caught, including
every mutant that removes a plan decision (D6, D7, D13, D14, D15, D10). Five
survived, all in `_linked_targets` normalization and predicate byte-exactness,
and three statements in `wiki_index.py` are never executed by the suite.

## Findings

### [MAJOR] Marker detection is an unanchored substring scan — prose that mentions both markers has the text between them silently destroyed

**Category:** Bug (data loss)
**File(s):** `scripts/wiki_index.py:128-129`, `scripts/wiki_index.py:150-151`
**Confidence:** [VERIFIED]
**Status:** New

**Description:**
`_classify_markers` and `_block_span` treat the marker strings as raw substrings
anywhere in the file. They are not anchored to a line, not required to be the
only content on their line, and not excluded from fenced code blocks. Any
`MEMORY.md` that contains both marker strings — for any reason — is classified
`ok` and the entire span between them is replaced by the generated block.

The PR's own `memory/CONVENTIONS.md` (added in `60daf43`) teaches downstream
users what the two markers are, which makes "a curated `MEMORY.md` that quotes
them" a foreseeable shape rather than a contrived one.

**Evidence:**
At HEAD_SHA `60daf43`, `scripts/wiki_index.py:128-129`:

```python
    begins = text.count(GENERATED_BEGIN)
    ends = text.count(GENERATED_END)
```

and `scripts/wiki_index.py:150-151`:

```python
    start = text.index(GENERATED_BEGIN)
    stop = text.index(GENERATED_END) + len(GENERATED_END)
```

Reproduction A — markers inline in one sentence. Input `MEMORY.md`:

```
# Index

The generator owns the region between `<!-- memory-index:generated start -->` and `<!-- memory-index:generated end -->` - do not edit inside it.

Keep this paragraph.
```

`regenerate()` returns `rc=0`, summary `['wrote: …MEMORY.md (regenerated block)']`
— **no `⚠`** — and the output is:

```
# Index

The generator owns the region between `<!-- memory-index:generated start -->

<!-- Generated by scripts/wiki_index.py. Edits between these markers are
     overwritten; everything outside them is preserved. -->

- [alpha](a.md) — first

<!-- memory-index:generated end -->
` - do not edit inside it.

Keep this paragraph.
```

The substring `` ` and ` `` is gone (asserted: `b"and \`" not in output` → True).
The result is stable on run 2 (`up-to-date`), so the loss is permanent and never
re-reported.

Reproduction B — markers on their own lines inside a fenced example:

```
# Index

Our convention:

```
<!-- memory-index:generated start -->
- [example](example.md) — this is documentation of the format
<!-- memory-index:generated end -->
```

Hand prose below.
```

`rc=0`, `wrote: … (regenerated block)`, no `⚠`, and the line
`- [example](example.md) — this is documentation of the format` is deleted from
the output.

**Impact:**
Silent, unattended, unwarned deletion of hand-written content from a curated
`MEMORY.md` — the exact failure class this PR exists to eliminate, on the exact
call site (`scripts/promote_learnings.py:484`) where `ai-os#138` happened.
`memory/` is symlinked into every installed brain by `install.py:54` and
`scripts/` is in `FRAMEWORK_PATHS`, so downstream instances receive this
verbatim and cannot patch it. The `--check` path gives no warning either: it
reports plain `stale`, indistinguishable from a normal regeneration.

**Reproduction Steps:**
1. `mkdir /tmp/f && cd /tmp/f`, add one note `a.md` with `name`/`description`
   frontmatter.
2. Write `MEMORY.md` containing one sentence that quotes both marker strings
   inline, with words between them.
3. `PYTHONPATH=scripts python -c "import wiki_index,pathlib; print(wiki_index.regenerate(pathlib.Path('/tmp/f')))"`.
4. Expected: refusal, or an append with a `⚠`. Actual: `rc=0`, "regenerated
   block", and the words between the two markers are gone.

**Recommended Fix:**
Anchor marker recognition to whole lines. Match per-line with
`^[ \t]*<!-- memory-index:generated (start|end) -->[ \t]*$` in
`_classify_markers`, and derive `_block_span` from those line offsets rather than
`str.index`. That eliminates Reproduction A outright and is a ~10-line change
with no behavioural effect on any of the 23 matrix rows.

Reproduction B (markers alone on their lines inside a fence) survives line
anchoring and needs one of: a fence-state scan when classifying; or — cheaper and
more in the spirit of D6 — a **splice-time safety check**: refuse (or append with
a `⚠`) when the region being replaced is not itself a previously generated block,
i.e. when its content does not consist of the `_BLOCK_NOTICE`, blank lines, and
lines the run emits or a recognised placeholder. That single check makes the
splice path as conservative as the migration path, which is the stated design
intent of the whole PR.

### [MINOR] `build_index()` interpolates frontmatter verbatim — a note whose `description` contains a marker string permanently wedges the index at rc 2

**Category:** Bug
**File(s):** `scripts/wiki_index.py:92`
**Confidence:** [VERIFIED]
**Status:** New

**Description:**
`build_index()` emits the frontmatter `name` and `description` with no
validation or escaping. If either contains `<!-- memory-index:generated start -->`
or `<!-- memory-index:generated end -->`, the generator writes a file with a
duplicated marker, which `_classify_markers` then classifies `malformed` on
every subsequent run. The generator poisons its own output and then refuses to
touch it.

**Evidence:**
At HEAD_SHA `60daf43`, `scripts/wiki_index.py:92`:

```python
        lines.append(f"- [{name}]({p.name}) — {desc}" if desc else f"- [{name}]({p.name})")
```

Note `a.md` with `description: see <!-- memory-index:generated end --> here`.

- Run 1: `rc=0`, `['wrote: …MEMORY.md (created)']`. File written with the end
  marker embedded in the bullet.
- Run 2: `rc=2`,
  `['⚠ malformed index markers: …MEMORY.md (2 end markers); refusing to write']`.
- Run 3: identical to run 2. The state is permanent until a human edits either
  the note frontmatter or the index.

`_wiki_common.split_frontmatter:48-52` (`k, _, v = raw.partition(":")`) keeps
everything after the first colon, so the full marker text — colons included —
reaches `desc` intact.

**Impact:**
The folder's index silently stops tracking new notes forever. Because
`scripts/promote_learnings.py:484` discards `regenerate`'s rc by design, the
promote still exits 0; the only signal is one `⚠` line in a summary nobody is
required to read. `memory/` is what agents read as ground truth, so a
permanently frozen index is a correctness regression, not just an annoyance. No
bytes are lost, and the operator is warned on every run, which is what keeps
this MINOR rather than MAJOR.

**Reproduction Steps:**
1. Create a note whose frontmatter `description` contains the literal string
   `<!-- memory-index:generated end -->`.
2. Run `regenerate()` twice on the folder.
3. Expected: the marker text is escaped, or the note is skipped with a warning.
   Actual: run 1 writes the poison, run 2 onward returns rc 2 and refuses.

**Recommended Fix:**
In `build_index()` (or in `regenerate()` before `render_block`), reject any
emitted line containing either marker string — replace the marker with an
HTML-safe form (e.g. `<!‑‑ … ‑‑>`), or drop the note from the block and emit a
`⚠` naming it. Three lines, no plan decision affected.

### [MINOR] De-duplication suppresses notes whose only "link" is inside a code fence or an HTML comment

**Category:** Bug
**File(s):** `scripts/wiki_index.py:67`, `scripts/wiki_index.py:217-222`,
`scripts/wiki_index.py:244-247`
**Confidence:** [VERIFIED]
**Status:** New

**Description:**
`_linked_targets` runs `_LINKED_TARGET_RE` over the entire preserved region with
no markdown context. A target appearing inside a fenced code block, an HTML
comment, or any other non-link context counts as "already linked" and removes
the real note from the generated block.

The plan's Open Question 1 explicitly accepted suppression for a note *mentioned
in passing in prose* ("the file demonstrably links it, so the index is not
lying"). That justification does not hold for a fenced example or a `<!-- TODO
-->` comment: the file does **not** link the note, and the index *is* lying by
omission.

**Evidence:**
At HEAD_SHA `60daf43`, `scripts/wiki_index.py:67`:

```python
_LINKED_TARGET_RE = re.compile(r"\]\(([^)]+\.md)\)")
```

Case A — fenced example. Folder has notes `a.md` and `b.md`. `MEMORY.md`:

````
# Index

Example of the format:

```markdown
- [alpha](a.md) - first
```
````

Result (`rc=0`, `⚠ appended`): the generated block lists **only**
`- [beta](b.md) — second`. `a.md` appears nowhere outside the code fence.

Case B — HTML comment. `MEMORY.md` is
`# Index\n\n<!-- TODO: drop the old [alpha](a.md) note -->\n`. Result: block
lists only `- [beta](b.md) — second`; `a.md` is suppressed by a comment that says
the opposite of "this is linked".

**Impact:**
A real note disappears from the folder index with no signal. `wiki_lint`
provides no compensating check: `wiki_lint._memory_referenced:39-46` scans
`MEMORY.md` with the same unqualified regex, so the note is not flagged as an
orphan either. Both tools are fooled by the same text, so nothing surfaces it.

**Reproduction Steps:**
1. Folder with `a.md` and `b.md`; `MEMORY.md` mentions `](a.md)` only inside a
   fenced code block.
2. `regenerate()`.
3. Expected: `a.md` in the block. Actual: `a.md` omitted permanently.

**Recommended Fix:**
Take the narrowing the plan itself pre-authorised in Open Question 1 — require
the match to begin a list item (`^\s*[-*+]\s*\[`), which excludes both fenced
example bodies indented under a fence and inline HTML comments in most real
cases. A fence-state scan is the complete fix but is larger; the bullet
restriction is one line and strictly better than today.

### [INFO] Confirmed: the `if new_text is None` branch in `regenerate()` is unreachable — recommend restructuring rather than deleting

**Category:** Maintainability
**File(s):** `scripts/wiki_index.py:330-334`
**Confidence:** [VERIFIED]
**Status:** Confirmed (pre-reported; verified, not rediscovered)

**Description:**
The report is correct. `compose` returns `None` only from its `malformed` branch
at `scripts/wiki_index.py:266-267`, which is gated by
`scripts/wiki_index.py:265`:

```python
    kind, reason = _classify_markers(existing_text)
```

`regenerate` performs the identical classification first, at
`scripts/wiki_index.py:305`:

```python
    kind, reason = _classify_markers(existing or "")
```

and returns rc 2 at `:306-309`. `existing or ""` differs from `existing` only
when `existing == ""`, and `_classify_markers("")` is `("none", "")` either way,
so the two calls always agree. Line-level tracing confirms
`scripts/wiki_index.py:331` is never executed by the 70-test suite.

**Evidence:**
`scripts/wiki_index.py:330` at HEAD_SHA `60daf43`:

```python
    if new_text is None:  # defensive — the malformed case is caught above
```

Mutation evidence that the branch is a *live* backstop rather than inert: with
`regenerate`'s early refusal at `:306-309` neutralised, the suite still passes
and `regenerate` still returns rc 2 — because `compose` returns `None` and this
branch catches it. It is genuine defence-in-depth against the two classification
sites diverging.

**Impact:**
Unexecuted code that a coverage gate would flag, and a duplicated invariant
(`_classify_markers` called twice on the same text) that a future edit could
desynchronise.

**Recommended Fix:**
Do **not** delete it. Prefer removing the duplication instead: drop the early
refusal at `:305-309` and let `regenerate` derive the rc-2 path solely from
`compose`'s `(None, "malformed:<reason>")` return. That makes `compose` the
single classification authority, makes lines 330-334 the *only* refusal path
(hence live and covered by the existing malformed tests), and preserves every
D7 behaviour. If the current shape is kept, add
`# pragma: no cover`-equivalent commentary noting the branch is deliberately
unreachable.

### [INFO] `regenerate()` writes non-atomically; the repo has an atomic precedent

**Category:** Bug (durability)
**File(s):** `scripts/wiki_index.py:341`
**Confidence:** [VERIFIED]
**Status:** New

**Description:**
`Path.write_text` truncates before writing. A crash, kill, or ENOSPC between
truncate and flush leaves an empty or partial `MEMORY.md`. The blast radius grew
with this PR: before it, the file's whole content was regenerable; now it holds
irreplaceable hand-written prose.

**Evidence:**
`scripts/wiki_index.py:341`:

```python
    index_path.write_text(new_text, encoding="utf-8", newline="")
```

In-repo precedent, `scripts/mark_harvested.py:140-142`:

```python
        tmp = path.parent / (path.name + f".{os.getpid()}.tmp")
        tmp.write_text(json.dumps(payload, indent=2), encoding="utf-8")
        os.replace(tmp, path)
```

**Impact:**
Low probability, high consequence, on an unattended path. Not a regression — the
pre-PR code had the same shape — but the value at risk changed.

**Recommended Fix:**
Mirror `mark_harvested.py`: write to `MEMORY.md.<pid>.tmp` with `newline=""`,
then `os.replace`. Five lines, stdlib-only, no plan decision affected.

### [INFO] `_block_span` does not consume a lone `\r` after the end marker

**Category:** Bug (cosmetic)
**File(s):** `scripts/wiki_index.py:152-155`
**Confidence:** [VERIFIED]
**Status:** New

**Description:**
`_block_span` consumes `\r\n` and `\n` after the end marker but not a bare `\r`.
On a CR-only file (classic-Mac endings) the `\r` survives into the preserved
suffix and the result carries a stray `\n\r` seam.

**Evidence:**
Input `# Index\r\r<BEGIN>\r\r- [stale](zz.md)\r\r<END>\rtail prose\r` yields
`…<!-- memory-index:generated end -->\n\rtail prose\r`. Verified stable across
three runs (`up-to-date` from run 2), so it converges and never grows.

**Impact:**
Cosmetic only. No loss, idempotent, `--check` green. Noted for completeness
because `_is_safely_replaceable`'s docstring at `scripts/wiki_index.py:207-208`
advertises lone-`\r` support and `_block_span` is the one place that does not
have it.

**Recommended Fix:**
Add `elif text[stop:stop + 1] == "\r": stop += 1`, or leave as-is and drop the
lone-`\r` claim from the `_block_span` neighbourhood.
